# Workflows

This directory contains helper scripts for generating simulation cfg files, running batches of DIMSWE simulations, building side-by-side comparison plots and movies from saved runs, and finding optimal model parameters with adjoint-based optimization (see [Parameter optimization workflow](#parameter-optimization-workflow)).

## Scripts

- `generate_cfgs.py`: expand a template simulation cfg into a set of concrete cfg files for a parameter sweep.
- `run_batch.py`: run either a manual list of cfg files or the manifest generated by `generate_cfgs.py`.
- `compare_runs.py`: create multipanel PNG comparison plots and WEBP movies from saved runs.
- `optimize_params.py`: find optimal coefficients or initial conditions against a set of truth runs.
- `validate.py`: rerun the model with optimized parameters and compute L2/Linf errors against the truth.
- `plot_validation.py`: plot truth vs optimized runs, error histories, optimizer histories and parameter recovery.
- `run_pipeline.sh`: chain truth generation, optimization, validation and plotting.
- `common.py`, `opt_helpers.py`, `losses.py`: shared helpers (pure-Python, Firedrake-side, and loss construction).
- `generate_cfgs.sh`, `run_batch.sh`, `compare_runs.sh`, `optimize_params.sh`, `validate.sh`, `plot_validation.sh`: thin Firedrake-environment wrappers for the Python scripts.

The Python entrypoints can also be called directly as scripts from the repository root, for example `python -I workflows/generate_cfgs.py ...`, which keeps imports isolated while still allowing the scripts to add the project root to `sys.path` explicitly.

## Directory conventions

Generated sweep cfg files are written under:

- `workflows/generated/<sweep-name>/`

Simulation outputs are written under:

- `runs/<run-name>/sim.h5`
- `runs/<run-name>/sim.pvd`

Each executed run also stores provenance files in its run directory:

- `run.cfg`: the resolved cfg used for execution
- `run-metadata.yaml`: run metadata including source cfg and output path

## Manual batch execution

Run a set of concrete cfg files directly with an explicit MPI rank count:

```bash
bash workflows/run_batch.sh 4 mtswe.cfg mtswe-cf.cfg mtswe-lp.cfg
```

Preview planned runs without executing:

```bash
bash workflows/run_batch.sh 4 --dry-run mtswe.cfg mtswe-cf.cfg
```

Skip runs whose `sim.h5` already exists:

```bash
bash workflows/run_batch.sh 4 --skip-existing mtswe.cfg mtswe-cf.cfg
```

`run_batch.py` is MPI-aware: rank 0 performs workflow-level directory creation, provenance-file writes, and skip checks, then all ranks synchronize before entering `run_model(parameters)` together for the actual Firedrake simulation.

## Sweep generation

An example sweep config is provided in `workflows/examples/sweep.cfg`.

Generate concrete cfg files and a manifest:

```bash
bash workflows/generate_cfgs.sh workflows/examples/sweep.cfg
```

This writes generated cfg files to `workflows/generated/<sweep-name>/` and creates `manifest.yaml` alongside them.

The sweep cfg uses dotted YAML paths to describe parameter ranges, for example:

- `spatial-discretization.order`
- `mesh.nx`
- `mesh.ny`
- `spatial-discretization.alpha_s`

It also supports `tied_parameter_sets` for values that should vary together as one sweep axis, for example coupling `mesh.nx` and `mesh.ny` so rectangular refinements stay aligned:

```yaml
tied_parameter_sets:
  - mesh.nx: 25
    mesh.ny: 25
  - mesh.nx: 50
    mesh.ny: 50
```

For refinement studies with direct timestepping, you can add `refinement_scaling` to preserve CFL-like refinement behavior, common final time, and common output times:

```yaml
refinement_scaling:
  refinement_keys: [mesh.nx, mesh.ny]
  reference_overrides:
    mesh.nx: 25
    mesh.ny: 25
    timestepping.dt: 400
    timestepping.num_steps: 1000
    output.output_freq: 50
```

This makes finer runs scale as:

- `timestepping.dt` decreases with refinement ratio
- `timestepping.num_steps` increases with refinement ratio
- `output.output_freq` increases with refinement ratio

These tied sets are combined with the ordinary Cartesian sweep parameters, and conflicting assignments for the same dotted path are rejected.

The current scripts write all generated cfg files to disk so that each run can be inspected and reproduced.

## Running a generated sweep

After generating a sweep, run the manifest with:

```bash
bash workflows/run_batch.sh 4 --manifest workflows/generated/mtswe-order-grid-flux/manifest.yaml
```

Use `--dry-run` first if you want to verify run names and output paths.

Manifest runs are written to the `run_directory` recorded in the manifest, which is `<output_root>/<run-name>` for the sweep's `output_root` (default `runs/`). Workflows that read the manifest, such as `optimize_params.py`, look for the runs there. Passing `--runs-root` explicitly moves manifest runs under that root instead; in that case, point the optimization spec at the moved runs with `truth.runs`. For plain cfg files, `--runs-root` defaults to `runs/`.

## Comparison plotting

An example comparison config is provided in `workflows/examples/compare.cfg`.

Create comparison plots and movies from existing runs:

```bash
bash workflows/compare_runs.sh workflows/examples/compare.cfg
```

Validate the comparison config without rendering outputs:

```bash
bash workflows/compare_runs.sh --dry-run workflows/examples/compare.cfg
```

The comparison config currently supports:

- `runs`: run directories containing `run.cfg` and `sim.h5`
- `quantities.fields`: field-like quantities such as prognostic variables and diagnostics
- `quantities.statistics`: scalar statistics stored in the checkpoint HDF5 file
- `time_selection.frames`: output indices to render as PNG frames
- `output.outdir`: destination directory for comparison artifacts

## Available quantities

The comparison script uses the same model-driven quantity discovery used by the existing plotting path:

- x variables from `model.get_x_var_list()`
- aux variables from `model.get_aux_var_list()` when `output_aux_vars` is enabled
- diagnostics from `model.get_diagnostics_list()`
- statistics from `model.get_statistics_list()`

This keeps comparison plotting aligned with the same quantities currently available through `plot_model.py`.


# Parameter optimization workflow

The optimization workflow finds the parameter values that best reproduce a set of "truth" runs, measured by a loss function. The parameters can be **model coefficients** (for example `hyperviscosity.c0` or `threewayphysics.gamma_r`) or the **initial condition**, either as analytic initial-condition parameters (for example the double-vortex offsets `initial-conditions.ox`/`oy`) or as the full discrete initial state.

It has three steps:

1. **Truth data**: generate (or reuse) runs over a range of parameter values.
2. **Optimization**: for each truth run and each loss function, find the optimal parameters.
3. **Validation**: rerun the model with the optimal parameters, compute L2/Linf errors against the truth, and plot the comparison.

## Quick start

All commands run from the repository root. Relative paths given on the command line are resolved against the repository root; relative paths inside a cfg file are resolved against that file's directory.

```bash
# Step 1: truth runs that vary moist-physics coefficients
bash workflows/generate_cfgs.sh workflows/examples/truth_coeff_sweep.cfg
bash workflows/run_batch.sh 4 --skip-existing --manifest workflows/generated/truth-physics/manifest.yaml

# Step 2: recover the coefficients with three different losses
bash workflows/optimize_params.sh 4 workflows/examples/optimize_coeff.cfg

# Step 3: validate and plot
bash workflows/validate.sh 4 runs/optimizations/physics-recovery
bash workflows/plot_validation.sh --sweep runs/optimizations/physics-recovery
```

Or run everything with one command:

```bash
bash workflows/run_pipeline.sh 4 workflows/examples/truth_coeff_sweep.cfg workflows/examples/optimize_coeff.cfg
```

Use `--skip-truth` as a fourth argument to reuse existing truth runs. The pipeline uses `--skip-existing` throughout, so it can be rerun after an interruption.

Examples for every target:

| Truth sweep | Optimization spec | Target |
|---|---|---|
| `examples/truth_coeff_sweep.cfg` | `examples/optimize_coeff.cfg` | `coeffs` |
| `examples/truth_ic_sweep.cfg` | `examples/optimize_ic_params.cfg` | `ic-params` |
| `examples/truth_ic_sweep.cfg` | `examples/optimize_ic_field.cfg` | `ic-field` (serial only) |

## Step 1: truth data

Truth runs are ordinary sweeps (see [Sweep generation](#sweep-generation)), so any dotted path, including coefficients and initial-condition parameters, can be varied. Three additions make parameter sweeps easier:

**Value specs.** Besides literal lists, sweep `parameters` accept:

```yaml
parameters:
  hyperviscosity.c0: [0.05, 0.07]                                  # literal values
  threewayphysics.gamma_r: {linspace: [0.0008, 0.0012, 3]}         # n evenly spaced values
  threewayphysics.qprecip: {geomspace: [0.00005, 0.0002, 3]}       # n geometrically spaced values
  initial-conditions.ox: {random: {low: 0.08, high: 0.12, n: 5, seed: 7}}  # seeded uniform samples
  threewayphysics.L: {random: {low: 5, high: 20, n: 4, seed: 1, log: true}} # log-uniform samples
```

Random samples need a `seed`, so a sweep always regenerates the same values.

**Strict paths.** By default (`strict_paths: true`) every swept, tied or fixed path, except `output.*`, must already exist in the template cfg, so a typo such as `hyperviscosity.cO` is an error instead of a silently ignored new key. Set `strict_paths: false` to allow new keys.

**Parameter kinds.** The manifest records each varied path under `parameter_kinds` as `ic` (`initial-conditions.*`), `coeff` (an entry of a forcing-term section with a `treat_as_coeffs` flag) or `other`, and lists the expanded values under `expanded_parameters`.

Things to keep in mind for truth runs:

- Run the truth with `treat_as_coeffs: false`. The optimizer turns on `treat_as_coeffs` for the sections it optimizes; both settings give the same equations.
- Use **short runs saved often**. The losses compare against saved outputs, so every observation step must be a multiple of `output.output_freq`. Each optimizer iteration integrates the training window forward and backward and holds every state of the window in memory.
- Optimization and validation reuse the truth run's discretization, mesh and time step. Truth and optimization at different resolutions are not supported.

**Existing runs as truth.** Any run directory containing `run.cfg` and `sim.h5` (for example one written by `run_batch.py`) can be used as truth, either through a manifest or by listing it in the optimization spec:

```yaml
truth:
  runs:
    - runs/truth/gamma-0p0008__qprecip-8eneg-05
    - {run_dir: runs/my-existing-run}
```

## Step 2: optimization

```bash
bash workflows/optimize_params.sh <mpi-ranks> <optimize.cfg> [--dry-run] [--skip-existing] [--check-gradient] [--only <substring>...]
```

`--dry-run` validates the spec against the truth cfgs and prints every planned job without running Firedrake. `--only` restricts the run to jobs whose names contain a substring. `--check-gradient` runs a Taylor test before optimizing.

### Optimization spec

```yaml
optimization_name: physics-recovery     # output goes to <output_root>/<optimization_name>/
truth:
  manifest: ../generated/truth-physics/manifest.yaml   # and/or runs: [...]
  mode: per-run                         # per-run: one optimization per truth run
                                        # joint: one optimization over all truth runs (coeffs only)
target: coeffs                          # coeffs | ic-params | ic-field
parameters:
  threewayphysics.gamma_r: {initial: 0.0015, bounds: [1.0e-5, 0.01], scale: 0.001}
  threewayphysics.qprecip: {initial: 0.00007, bounds: [1.0e-6, 0.001], scale: 0.0001}
  threewayphysics.L: {fixed: 10.0}
window:
  start_index: 0                        # truth output index where training starts
  num_steps: 20                         # model steps in the training window
losses:
  - {type: final}
  - {type: windowed, window_steps: 4}
  - {type: trajectory, obs_every: 2}
normalize: true
overrides: {}                           # optional dotted-path changes to the truth cfg
optimizer:
  method: L-BFGS-B                      # any scipy.optimize.minimize method using gradients
  gtol: 1.0e-8
  ftol: 1.0e-12
  maxiter: 60
  check_gradient: false
  tolerance: relative                   # gtol relative to the initial gradient (default), or absolute
output_root: runs/optimizations
```

Parameter entries:

- `initial`: the starting value (defaults to the truth cfg value).
- `bounds`: `[low, high]` (`null` for unbounded). Only `coeffs` supports bounds; they replace the forcing term's built-in bounds, and the starting value must lie inside them.
- `scale`: the optimizer works with `value / scale`. Pick something like the parameter's typical size, so parameters of very different magnitude (`qprecip` ~ 1e-4 next to `L` ~ 10) are equally well conditioned. Defaults to `|initial|`.
- `fixed: <value>` (or `fixed: true`): hold the parameter at that value.
- For `coeffs`, every coefficient of a section being optimized is part of the problem. Coefficients you don't list keep their truth value and stay fixed.

### Targets

| Target | What is optimized | Gradient | MPI |
|---|---|---|---|
| `coeffs` | forcing-term coefficients (`hyperviscosity.{s,c0}`, `threewayphysics.{gamma_r,qprecip,L}`) | adjoint | any rank count |
| `ic-params` | numeric `initial-conditions.*` parameters (for example `ox`, `oy`) | adjoint, then UFL derivative of the IC expressions | any rank count |
| `ic-field` | the full discrete initial state, starting from the analytic IC with the listed parameter values | adjoint | **1 rank only** |

For `ic-params`, the initial-condition expressions are rebuilt with the parameters as R-space Functions. The tangent `dx0/dp` is the projection of `ufl.derivative` of those expressions, and the parameter gradient is `(dx0/dp)^T dJ/dx0`. There are no finite differences. Only the prognostic variables depend on the parameters; coriolis and topography are fixed when the model is initialized.

For `ic-field`, the optimization vector is the rank-local array of dofs, so the script refuses to run on more than one rank. The scaling is per variable (each dof divided by the largest magnitude of its variable in the truth).

### Loss functions

The losses differ in how often the model output is compared with the truth:

| `type` | Comparison | Blocks | Targets |
|---|---|---|---|
| `final` | once, at the end of the training window | 1 block of `num_steps` | all |
| `windowed` | at the end of each `window_steps` window; each window **restarts from the truth** | `num_steps / window_steps` blocks | `coeffs` |
| `trajectory` | every `obs_every` steps along one uninterrupted run | 1 block of `num_steps` | all |

`windowed` is not allowed for initial-condition targets, because restarting every window from the truth leaves nothing to learn about the initial state. `trajectory` with `obs_every` equal to `output_freq` compares at every saved truth output. Add a `label` to a loss to tell apart two losses of the same type.

Each observation contributes `0.5 * sum_var w_var * ||x_var - truth_var||^2`. With `normalize: true`, `w_var = 1 / max ||truth_var||^2` over the observed truth states and the loss is averaged over observations. This keeps `h` (~750 m) from dominating `v`, and makes losses comparable across loss types. With `normalize: false`, the plain unweighted L2 misfit is used.

### Outputs

```
runs/optimizations/<optimization_name>/<truth-run>__<loss-label>/
  optimize.cfg        resolved spec, truth run(s), loss, and observation schedule for this job
  result.yaml         initial/optimal/true values and errors, initial and final loss, scipy status
  history.csv         loss, gradient norm and parameter values per optimizer iteration
  optimal.cfg         the (overridden) truth cfg with the optimal values written back
  initial_guess.cfg   the same with the initial values
  optimal_ic.h5       optimized initial state (ic-field)
  initial_guess_ic.h5 starting initial state (ic-field)
  taylor-test.yaml    gradient check (with --check-gradient or check_gradient: true)
```

In `joint` mode the job directory is named `joint__<loss-label>` (or `<truth.label>__<loss-label>`), and true values are reported only when all truth runs share them. All jointly optimized truth runs must share the mesh, discretization, time step and output frequency, and be loaded with the same MPI rank count that wrote them.

### When the optimizer stops immediately

Before optimizing, each job prints the loss, the gradient norm and each free parameter's gradient component at the initial guess, and records them as `initial_gradient` in `result.yaml`. L-BFGS-B stops before taking a step (`CONVERGENCE: NORM OF PROJECTED GRADIENT <= PGTOL`) when the largest projected gradient component is already below `gtol`. The workflow handles the usual causes as follows:

- **Small but real gradient.** With `optimizer.tolerance: relative` (the default), `gtol` is a fraction of the initial gradient's largest component, so the overall size of the loss can't end the run early. Set `tolerance: absolute` to pass `gtol` to scipy unchanged.
- **Exactly zero gradient.** The job stops with an error instead of reporting convergence. The loss doesn't depend on the free parameters at the initial guess. For `threewayphysics`, rain only forms where cloud water exceeds `qprecip`. If that never happens in the training window, `gamma_r` and `qprecip` have no effect and the gradient is zero. Lengthen `window.num_steps`, start closer to the truth (for example a smaller `qprecip`), or check that the section is in `model.forcing_terms`.
- **A parameter starting on a bound.** L-BFGS-B projects the gradient onto the bounds, so a parameter that starts on a bound, with a gradient pointing outward, can't move. A warning is printed; start strictly inside the bounds.

`result.yaml` records `optimizer.gtol_used` and `optimizer.nit`. A warning is printed when a job finishes after zero iterations.

### Checking gradients

`--check-gradient` runs a Taylor test in a fixed random direction before optimizing, and writes `taylor-test.yaml`. The remainder `|J(z + eps d) - J(z) - eps dJ.d|` should fall at rate ~2. Rates near 1 indicate a wrong gradient; very small or noisy remainders mean `eps` has reached round-off.

## Step 3: validation and plotting

```bash
bash workflows/validate.sh <mpi-ranks> <job-dir-or-optimization-root>... [--num-steps N] [--no-initial-guess] [--fields h v ...] [--skip-existing] [--dry-run]
bash workflows/plot_validation.sh <job-dir-or-optimization-root>... [--fields h ...] [--frames 0 10 30] [--movie] [--statistics ...] [--sweep]
```

`validate.py` reruns each job's truth case from the truth's initial time and mesh, using the optimal parameters and (unless `--no-initial-guess`) the initial-guess parameters as a baseline. `--num-steps` sets the run length; errors are computed while truth outputs exist, so outputs past the training window measure forecast skill. Run `ic-field` validations with the same MPI rank count used to optimize them.

At every output, each compared field gets the metrics below. By default every x variable and diagnostic is compared (for moist models this includes `Qv`, `Qc`, `Qr`, their per-unit-mass forms `Qv_l`, `Qc_l`, `Qr_l`, and `qsat` and `rh`), except the fixed fields `coriolis` and `bottom_topography`, which never change. `errors-summary.yaml` records the compared fields grouped as `prognostic`, `moisture` and `diagnostic`.

| Metric | Definition |
|---|---|
| `l2` | `||a - b||_L2` with the model's quadrature |
| `rel_l2` | `||a - b||_L2 / ||b||_L2` |
| `linf` | `max |a - b|` over the dofs (pointwise vector magnitude for vector fields) |
| `rel_linf` | `max |a - b| / max |b|` |

`a` is the validation run and `b` the truth. Scalar statistics (`total_energy`, `total_h`, ...) get `diff` and `rel_diff` at the output times.

Validation outputs, under `<job-dir>/validation/<case>/` with case `optimal` or `initial-guess`:

```
run.cfg, sim.h5, sim.pvd   the validation run
errors.csv                 per-output errors for every field and statistic
errors-summary.yaml        final, max and mean of every error, plus maxima inside the training window and after it
errors.h5                  difference fields (run - truth) per output, used by the plots
```

It also writes `<optimization-root>/summary.csv`, with one row per job and case: true and recovered values, recovery errors, losses, optimizer counts, and final/max relative errors per field.

Plots, under `<job-dir>/plots/`:

- By default the per-job plots cover the prognostic variables and the moisture fields (`v`, `h`, `S`, `Qv`, `Qc`, `Qr`, `Qv_l`, `Qc_l`, `Qr_l`, `rh`, `qsat` for moist models). Use `--fields` to choose others, for example `--fields Qv rh eta`.
- `<field>__frame-NNN.png`: truth, optimized, initial guess and optimized − truth side by side. Value panels share one colour scale; the difference uses a diverging scale centred on zero. The default frames are the first output, the end of the training window, and the last output. `--movie` also writes `<field>__compare.webp`.
- `errors__<field>.png`: relative L2 and Linf errors over time for the optimized run and the initial guess, with the training window shaded.
- `statistics__<name>.png`: statistic time series for truth, optimized and initial guess.
- `history.png`: loss and gradient norm per iteration. `parameters.png`: each parameter's path towards its true value.

With `--sweep`, under `<optimization-root>/plots/`:

- `recovery__<parameter>.png`: recovered vs true values for every truth run, one marker per loss.
- `errors-by-loss__<field>.png`: final relative L2 error per truth run and loss.

Run `plot_validation.sh` on one process; it reads whole checkpoints.

## Changes to the DIMSWE package used by the workflow

- `dimswe.optimize.ObservationL2Objective` compares with data at any set of steps within each block, with optional per-variable weights. The adjoint sweep adds `M^{-1} r_n` to the adjoint at every observation step. `L2Objective` is unchanged and remains the final-state special case.
- `dimswe.optimize.ParametricInitialCondition` maps analytic initial-condition parameters to the discrete initial state, with UFL-derived tangents.
- `_ODEConstrainedOptimization.optimize` accepts `maxiter`, `bounds`, `scaling_factors`, `free_mask`, `ic_map`, `callback` and `return_result`, and supports `opt_type='ic-params'`. `reduced_problem` builds the scaled, reduced problem, and `taylor_test` checks its gradient.
- `get_model(..., mesh=...)` and `get_mesh_and_spaces(..., mesh=...)` reuse an existing mesh (for example one loaded from a truth checkpoint), so truth states can be used directly.
- `run_model(parameters, mesh=None, initial_state=None, output_callback=None)` builds on a given mesh, can overwrite the initial state, calls a hook at every output, and returns the model. The defaults keep the previous behaviour.

## Limitations

- Truth and optimization must use the same resolution and discretization.
- Coefficients must be R-space scalars (all current forcing-term coefficients are).
- `ic-field` is serial only. `ic-params` and `coeffs` run with MPI.
- Checkpoints that pair a saved state with the truth mesh (`optimal_ic.h5`) must be loaded with the MPI rank count that wrote them.
- Every state of a training window is kept in memory, so keep `window.num_steps` modest.

## Notes

- These scripts assume the Firedrake environment is activated through the provided shell wrappers.
- The repository guidance says `runs/` holds generated data and should not be committed.
- The comparison workflow (`compare_runs.py`) is designed around comparing one quantity across multiple runs side-by-side; for truth-vs-optimized comparisons use `plot_validation.py`, which shares colour scales across panels.
